# Vishenka Medical Server

Клиент-серверный комплекс для ведения карт пациентов, автоматического анализа жалоб с помощью языковой модели и сквозного шифрования переписки медицинского персонала.

Проект не вводит новых криптографических или ИИ-методов. Его ценность — в интеграции готовых технологий: Signal Protocol, локальная LLM через Ollama и реляционная база карт пациентов объединены в одну систему так, что переписка врачей недоступна серверу, а запрос к модели не содержит идентифицирующих данных пациента.

## Возможности

- Регистрация и поиск пациента по СНИЛС с проверкой контрольного числа.
- Хранение карт посещений (название, описание, заметка врача, признак важности).
- Автоматический анализ жалоб локальной моделью qwen2.5:14b с учётом истории болезней пациента.
- Сквозное шифрование переписки на Signal Protocol (X3DH + Double Ratchet).
- Офлайн-доставка зашифрованных сообщений.
- Формирование текстового документа посещения по шаблону.

## Архитектура

Комплекс состоит из четырёх независимых компонентов. У каждой подсистемы своя база данных и свой сетевой порт, поэтому сбой одного модуля не затрагивает остальные.

### 1. Модуль карт пациентов (Patient Records)

Отвечает за регистрацию пациента и ведение истории посещений.

**Регистрация по СНИЛС с проверкой контрольного числа.** СНИЛС содержит 11 цифр, где последние две — контрольные. Проверка выполняется по стандартному алгоритму: первые девять цифр умножаются на коэффициенты 9, 8, 7, 6, 5, 4, 3, 2, 1; сумма приводится по модулю 101 с частными случаями (сумма < 100 — контрольное число равно сумме; остаток 100 приводится к 0). В самописных реализациях часто теряют граничные случаи `сумма = 100` и `сумма = 101`, что приводит к ложному отклонению корректных номеров.

**Карта посещения** содержит:

- название визита;
- описание;
- заметку врача;
- признак важности.

История болезни пациента хранится в структурированном виде и используется при формировании контекста для ИИ-анализа.

### 2. Модуль защищённой переписки (Secure Messaging)

Реализует сквозное шифрование на **Signal Protocol**.

**X3DH (Extended Triple Diffie-Hellman)** устанавливает общий секрет между двумя сторонами асинхронно — получатель может быть офлайн в момент отправки первого сообщения. Инициатор использует опубликованный набор предключей получателя: Identity Key, Signed PreKey и, при наличии, One-Time PreKey. Из четырёх Diffie-Hellman вычислений выводится общий секрет, который затем инициализирует Double Ratchet.

**Double Ratchet** обеспечивает два свойства:

- **Forward secrecy**: каждый шаг симметрической цепочки выводит новую цепочку и ключ сообщения; старые ключи удаляются. Компрометация текущего ключа не раскрывает прошлые сообщения.
- **Post-compromise security**: при получении сообщения с новым DH-ключом выполняется DH-ratchet — генерируется новая пара ключей, и злоумышленник, знавший предыдущее состояние, теряет возможность читать дальнейшую переписку.

**Офлайн-доставка** означает, что сервер хранит зашифрованные сообщения в очереди для получателя и не участвует в выводе ключей. Сервер не может расшифровать содержимое - он оперирует только метаданными, необходимыми для маршрутизации.

### 3. Модуль анализа жалоб (LLM Analyzer)

Анализ жалоб выполняется локальной моделью **qwen2.5:14b** через **Ollama**. Модель запускается на том же хосте или в той же инфраструктуре, что и сервер, без обращения к внешним API.

**В контекст передаются:**

- текст жалобы;
- фрагменты истории болезни (диагнозы, предыдущие реакции, хронология).

История болезни используется как контекст, чтобы модель могла учитывать предшествующие состояния, но связь «история ↔ конкретный пациент» остаётся только в базе карт и не попадает в промпт.

Модель qwen2.5:14b выбрана как компромисс между качеством и требованиями к ресурсам: в независимых оценках она показывает стабильные результаты при работе на потребительском оборудовании без GPU, в том числе в задачах извлечения структурированной информации.

### 4. Модуль формирования документов (Document Builder)

Формирует текстовый документ посещения по шаблону. Шаблон определяет структуру: блок жалоб, блок анамнеза, блок заключения, блок рекомендаций. Данные подставляются из карты посещения и, при необходимости, из результатов ИИ-анализа. Модуль не содержит собственной базы — он читает данные из модуля карт через внутренний интерфейс.

## Модель угроз и границы доверия

| Компонент | Что видит | Чего не видит |
|---|---|---|
| Сервер переписки | Метаданные: кто, кому, когда, размер | Содержимое сообщений (зашифровано Signal Protocol) |
| Модуль LLM | Текст жалобы и обезличенный контекст истории | ФИО, СНИЛС, адрес, прямые идентификаторы |
| Модуль карт | Полные данные пациента | Ключи переписки, содержимое чатов врачей |
| Администратор БД карт | Записи карт | Содержимое переписки |

Сервер переписки не хранит ключи и не может расшифровать сообщения даже при полном доступе к своей базе. Модуль LLM не получает идентифицирующих данных, поэтому даже при компрометации локальной модели (например, через логи) утечка ограничена клиническим текстом без привязки к личности.

## Технологический стек

- **Язык**: Java.
- **LLM**: Ollama, модель `qwen2.5:14b`, локальный HTTP-эндпоинт `http://localhost:11434`.
- **Криптография**: реализация Signal Protocol (X3DH + Double Ratchet) — libsignal.
- **Базы данных**: отдельные экземпляры для карт, очереди сообщений и метаданных; СУБД - CockroachDB, PostgresSQL.
- **Порты**: у каждого модуля свой сетевой порт, что упрощает развёртывание и мониторинг.
